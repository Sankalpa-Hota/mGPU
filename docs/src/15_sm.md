# 15 SM (streaming multiprocessor)

## What this block is, in plain words

The SM is where the blocks of the last ten chapters become a processor. It holds two **sub-cores**; each runs one workgroup of up to 4 warps and has its own scheduler, SIMT stack, register file, ALU, SFU, LSU, shared memory and barrier. The two sub-cores share one instruction cache and one L1 data cache, and the SM has a single memory port to the rest of the chip.

## Inside the SM

```tree
sm | 2 sub-cores, shared caches | root
  Sub-core x2 | one workgroup each | comp
    Warp scheduler -> operand collector -> ALU / SFU / LSU / barrier | issue path | comp
    SIMT stack | pc and mask of each warp | comp
    Shared memory 512 B | LDS / STS | comp
  Instruction cache | shared by the two schedulers | comp
  Line arbiter | two LSUs -> L1 | comp
  L1 data cache | write-through | comp
  Line arbiter | I-cache fills + L1 traffic -> SM memory port | comp
```

## Who talks to whom inside the sub-core

| From | To | What |
|---|---|---|
| Scheduler | I-cache | fetch pc of a warp |
| Scheduler | collector | issue (instruction, warp, pc, active mask from the SIMT stack) |
| Collector | ALU / SFU / LSU / barrier | instruction + operands (unit 3 = barrier, always ready) |
| ALU | SIMT stack | branch, JMP, EXIT with the taken lanes |
| Barrier | SIMT stack + scheduler | release: advance pc and end the control wait of the released warps |
| ALU / SFU / LSU | register file | results; the register file tells the scheduler which pending bits to clear |
| LSU | shared memory / L1 | LDS-STS / LD-ST |

## Integration decisions and why

| Decision | Why |
|---|---|
| One workgroup per sub-core | Shared memory and the barrier then belong to exactly one workgroup; no partitioning logic. |
| `wg_done` only when every warp has exited **and** the LSU and SFU are idle | Stores still in flight must land before the dispatcher (and the driver, through the fence) believe the work is done (`BUG_WG_DONE_EARLY`). |
| Active mask taken from the SIMT stack at issue | The units write only active lanes (`BUG_MASK_NOT_PASSED` passes all lanes: divergent kernels corrupt registers). |
| I-cache and L1 invalidated at kernel start | The CPU writes new code and data between kernels; the L1s are not coherent (`BUG_L1_NO_INVALIDATE`). |
| The line arbiter holds its choice while waiting, one request outstanding | The valid/ready rule (lesson of issue R3) applied from the start. |

## The testbench: real kernels against an instruction-set simulator

This is where the testbench changes nature: the stimulus is **programs**. `tb/common/mgpu_asm.sv` is a small assembler with labels; `mgpu_kernels.sv` holds the kernels; `mgpu_iss.sv` runs every thread on its own (no warps, no SIMT stack) and is the golden model. After the last workgroup finishes, the **whole memory** is compared with the ISS at once, like a CPU reading results after the completion interrupt.

| Kernel | What it stresses |
|---|---|
| vector_add, saxpy | loads, stores, coalescing, MUL |
| reduction | shared memory, barrier inside a loop, divergent `if (lid < s)` |
| divergence | if/else, nested if/else in the taken path (stack depth 5), loop with a per-thread trip count, REM |
| sfu | DIV, REM, ISQRT on random 32-bit values |
| exit_barrier | whole warps and lanes 6-7 exit before a barrier; the others exchange values through shared memory |
| smem_conflict | all 8 lanes of a warp in one shared-memory bank: 8 passes per access |
| random | seeded random ALU/SFU work, divergent ifs and per-lane loops; every working register is dumped to memory |

Two lessons from building this bench: the random generator first let random operations overwrite the register holding the argument address, so stores went to wild addresses, including the code (self-modifying code: the ISS saw the new instructions, the I-cache rightly kept the old ones). And the coverage bin "SIMT depth 5" stayed at 0 until the nested if/else was put in the *taken* path with its own join point: the reuse refinement of the SIMT stack (correctly) merges joins that coincide.

## Results

| Item | Result |
|---|---|
| Regression | 4 tests x 3 seeds = 12 runs, all PASS: 21 kernel runs (7 kernels x 1, 2, 4 warps per workgroup) and 12 random kernels per seed, memory identical to the ISS |
| Measured IPC | 0.19 (SFU-bound) to 0.51 (reduction) instructions per cycle per SM |
| Merged coverage | 100% (19 of 19) |
| `BUG_MASK_NOT_PASSED`, `BUG_WG_DONE_EARLY`, `BUG_L1_NO_INVALIDATE` | all caught |

# Teaching section: the SM in context

## The block and its pins

```pins
block: SM | sm.sv · 2 sub-cores · shared I-cache (16 lines) · shared L1 (16 sets, 2-way) · 1 memory port
in: launch_valid, launch_sub | dispatcher (via mgpu_top) | start a workgroup, and on which of the 2 sub-cores
in: launch_wg_id, launch_nwarps, launch_pc, launch_arg | dispatcher | workgroup id, warp count, kernel start PC, argument pointer
in: invalidate | mgpu_top (kernel_start) | clear the I-cache and the L1 at a new kernel
in: mreq_ready | crossbar | the crossbar's bank accepted the request
in: mrsp_valid, mrsp_data | crossbar | line answer for this SM
out: wg_done[1:0] | dispatcher | pulse per sub-core when its workgroup finished
out: busy | GMU / dispatcher | any sub-core active (used for power gating)
out: mreq_valid, mreq_addr, mreq_we, mreq_wdata, mreq_wstrb | crossbar | one line request: I-cache fill or L1 traffic
out: stat_issue[1:0], stat_l1_hit_pulse, stat_overflow | performance counters | issue per sub-core, L1 hits, SIMT stack overflow
```

```pins
block: Sub-core | subcore.sv · 1 workgroup · up to 4 warps x 8 lanes
in: launch_valid, launch_wg_id, launch_nwarps, launch_pc, launch_arg | sm | start a workgroup on this sub-core
in: f_ready, f_rsp_valid, f_rsp_instr | icache | fetch accepted / instruction word returned
in: mreq_ready, mrsp_valid, mrsp_data | line_arbiter (L1) | LSU line request accepted / line or acknowledge returned
out: f_valid, f_pc | icache | fetch request from the warp scheduler
out: mreq_valid, mreq_addr, mreq_we, mreq_wdata, mreq_wstrb | line_arbiter (L1) | the LSU's coalesced line request
out: wg_done, active | sm | workgroup finished (pulse) / running
out: stat_issue, stat_simt_depth, stat_smem_passes, stat_lsu_lines, stat_overflow | statistics | issue, deepest SIMT stack, shared-memory passes, LSU lines, overflow
```

Read it like a chip pinout: inputs are on the left, outputs on the right. A valid/ready pair is drawn on the side of its `valid` signal; `ready` always flows the other way. The orange name over each pin is the block on the other end of the wire.

## Where it sits in the pipeline

The sub-core pipeline, one instruction's journey:

```hflow
Warp scheduler | picks a ready warp -PC-> I-cache | shared by 2 sub-cores -instr-> Operand collector | scoreboard, reads registers -ex_unit-> ALU / SFU / LSU / Barrier | execute | you
(cont.) ALU / SFU / LSU / Barrier | execute | you -wb-> Operand collector | writes rd -br-> SIMT stack | pc and masks
```

And the SM around the two sub-cores:

```hflow
Sub-core 0 and 1 | LSU line requests -line req-> Line arbiter | u_l1_arb -line-> L1 data cache | 1 per SM -miss/write-> Line arbiter | u_mem_arb, with I-cache -line req-> Crossbar | to L2
```

| Inside the SM | Count | Shared by |
|---|---|---|
| Sub-core (scheduler, collector, ALU, SFU, LSU, shared memory, barrier, SIMT stack) | 2 | private |
| Instruction cache | 1 | both sub-cores (2 ports) |
| L1 data cache | 1 | both sub-core LSUs, through `u_l1_arb` |
| Memory port | 1 | I-cache fills and L1 traffic, through `u_mem_arb` |

## Who uses it and for what

| Who | Through which pins | What for |
|---|---|---|
| Dispatcher (via mgpu_top) | launch_*, wg_done | `launch_slot[0]` picks the SM, `launch_slot[1]` becomes `launch_sub`; the four `wg_done` bits come back as slots. |
| GMU | busy | Knows when an SM is idle so it can be powered down. |
| mgpu_top | invalidate | `kernel_start` (new kernel accepted) clears I-caches and L1s. |
| Crossbar (16) | mreq_* / mrsp_* | The SM's only path to L2 and DRAM. |
| Performance counters | stat_* | Issue count, L1 hits, SIMT overflow. |
| Inside the SM: sub-core | all its pins | One sub-core runs one workgroup at a time; `subcore.sv` instantiates simt_stack, warp_scheduler, regfile_collector, alu, sfu, lsu, shared_mem, barrier. |
| Inside the SM: line_arbiter | in_* / out_* | Two instances: 2 LSUs into the L1, and I-cache plus L1 into the memory port. |

## Design details

- **Unit routing in the sub-core.** The collector produces one `ex_valid` and an `ex_unit` number; each unit sees `ex_valid && ex_unit == k`, and `ex_ready = {1'b1, lsu_ready, sfu_ready, alu_ready}`. The barrier (unit 3) is always ready because an arrive is just a pulse.
- **Three write-back ports.** ALU, SFU and LSU each own one write-back port (0, 1, 2) into the collector, so results from different units never fight for a single bus. The scheduler sees the same write-backs (`wb_fire`) to clear pending registers.
- **The SIMT stack owns control.** It holds `pc` and `mask` per warp; the scheduler advances PCs through `adv_mask`, the ALU reports branches on `br_*`, and the barrier's `release_mask` also counts as "control done" so released warps continue.
- **Workgroup lifetime.** `launch_valid` loads the context (`ctx_wg`, `ctx_arg`, `ctx_nw`) used by S2R, and sets `active`. `wg_done` pulses when no warp is live and both the LSU and SFU are idle. Waiting for the LSU matters: a store may still be on its way to memory after the last EXIT.
- **line_arbiter.** Round-robin between N requesters, but only one request outstanding: after a grant it is `busy` until the answer, which goes back to the `owner`. A request offered but not yet accepted is `held`, so the payload stays stable. Simplicity is the goal: no ids are needed because only one answer can be pending.
- **Shared I-cache and L1.** Two sub-cores running the same kernel fetch the same code, so sharing one I-cache gives free hits. Sharing the L1 lets workgroups on one SM reuse each other's data, at the cost of contention.
- **Invalidate at kernel start** is the whole coherence story between SMs: each kernel starts with empty L1s and I-caches, so it never sees stale data or stale code from a previous kernel.

## Questions: what if we did it differently?

**Q1. What if each sub-core had its own L1 instead of one shared L1?**
No arbiter in front of the L1, so no contention between sub-cores, and each cache could be simpler. But the two workgroups could not share cached lines, and total capacity would be split. NVIDIA SMs share one L1/shared-memory block across their four processing blocks for this reason. Testbench: per-sub-core L1 hit statistics and two memory streams into `u_mem_arb`.

**Q2. What if the SM had several memory requests in flight instead of one?**
The line arbiters allow only one outstanding request, so an I-cache miss waits behind a slow L1 miss. With ids (or a request queue and MSHRs in the L1) the SM could overlap misses. That means an id field on the SM port, an out-of-order capable crossbar (it already returns by id), and order rules for same-address accesses. Testbench: answers in random order with id matching.

**Q3. What if the line arbiter used fixed priority (for example I-cache first)?**
Giving fetch priority is reasonable: without instructions nothing runs. But under heavy L1 miss traffic and constant I-cache misses, the L1 side could starve. Round-robin bounds waiting to one turn. Alternatives: *weighted round-robin*, or *age-based* arbitration. Testbench: a fairness assertion on maximum wait.

**Q4. What if a sub-core could run more than one workgroup at a time?**
Real SMs keep many workgroups resident to hide latency (occupancy). Here a sub-core holds one workgroup and up to 4 warps. More residency means per-warp workgroup context instead of one `ctx_*` set, partitioned shared memory and barriers per workgroup, and a `wg_done` per workgroup. Testbench: the dispatcher model must track several workgroups per slot.

**Q5. What if instructions were issued to two units per cycle (dual issue)?**
The collector routes one instruction per cycle. Dual issue would need two read port sets on the register file (or banking), two `ex_*` buses and a check that two instructions are independent. Gains: ALU and LSU work overlap. The measured IPC of 0.19 to 0.51 shows the pipeline is mostly latency-bound, so more warps would help more than dual issue.

**Q6. What happens with `BUG_MASK_NOT_PASSED`?**
The collector always receives an all-ones mask. After a divergent branch, lanes that should be inactive still execute and write registers and memory. Kernels with an `if (tid < n)` guard write past the end of arrays, and divergent if/else bodies corrupt each other's results. The kernel tests compare memory with the ISS and see the extra or wrong writes.

**Q7. What happens with `BUG_WG_DONE_EARLY`?**
`wg_done` fires as soon as all warps have exited, without waiting for the LSU and SFU. A store still in flight may reach memory after the host (or the next workgroup) already thinks the work is finished, so a check right after completion sees missing results. Symptom: rare, timing-dependent wrong data at the end of a kernel, typically the last store.

**Q8. What happens with `BUG_L1_NO_INVALIDATE`?**
The L1 keeps its lines across kernels. If one kernel writes data through another SM (whose L1 copy was never updated) or the CPU changes memory between kernels, the next kernel reads stale lines from this L1. It looks like "second kernel sees old input". The multi-kernel tests catch it.

**Q9. What if L1s were kept coherent in hardware (MESI) instead of invalidated per kernel?**
Each L1 line would get a state, the L2 would keep a directory of sharers, and the crossbar would carry invalidations back to SMs. That allows producer/consumer communication between SMs inside one kernel, at significant cost in area, traffic and verification effort. GPUs usually prefer *software coherence* plus L2 atomics and memory fences. Testbench: multi-SM sharing tests and coherence-protocol assertions.
